# Автоматический Возврат MAX В Webhook

Доступен во внешнем плагине **0.2.4**. Включается явно для нужного профиля:

```yaml
platforms:
  max:
    extra:
      webhook_auto_fallback: true
      webhook_auto_return: true
```

URL, секрет и inbox остаются прежними. Флаг не задаётся через глобальное
окружение и не включает автопереключение остальных MAX-профилей.

## Переходы

При недоступности входа сохраняется проверенный порядок: снять только свою
подписку, подтвердить отсутствие всех подписок, запустить polling.

Для возврата нужны три последовательных успешных защищённых проверки входа
и не менее **120 секунд** после запуска резерва. Проверки идут каждые 20 секунд;
реальное время зависит от тайм-аутов. Это выдержка от колебаний сети, не SLA.

Перед регистрацией Webhook останавливается **только polling-задача**, не Hermes
и не работники очереди. В SQLite заранее фиксируется намерение `returning=1`.
После POST нужен GET, подтверждающий ровно ожидаемую подписку. Только тогда
снимаются latch и намерение, а транспорт объявляется Webhook.

Если POST завершился ошибкой, GET всё равно обязателен: сервер мог применить
подписку до разрыва. Если результат GET неизвестен или есть чужая подписка,
polling остаётся остановленным до разрешения неопределённости. Чужие подписки
не удаляются. Если подтверждено отсутствие подписок, возобновляется polling,
с новой выдержкой перед следующей попыткой возврата.

После перезапуска незавершённый переход сверяется с настоящим MAX до старта
polling. Marker, inbox и дедупликация не меняются при переключении. Запущенные
обработчики продолжаются; неизвестные внешние действия не повторяются.

`/maxstatus` показывает транспорт, состояние резерва и включение автовозврата.
При неопределённом переходе подпись «polling» не означает, что запросы идут:
отдельно показано состояние polling-задачи. Недоступность самого MAX API
не позволяет гарантировать связь или немедленно разрешить переход.

## Учёт Сообщений Занятой Сессии

Настоящий Hermes может потребить follow-up через busy-handler без запуска
отдельного задания, например включить распознанный голос в текущий ответ.
`_gateway_accepted=False` в этом случае не доказывает отказ.

Плагин наблюдает результат штатного busy-handler. Только явные `handled=True`
и `_bot_loop_admitted=True` дают отдельный статус **consumed**, если отсутствует
подтверждение нового задания. Это не `processed` и не обещание отдельного ответа.
Неавторизованный или действительно не принятый ввод не получает такой статус.
Состояние сохраняется, не воспроизводится после перезапуска и видно в диагностике.
Если позже придут processing hooks, они уточнят состояние до processing/итога.
Старые строки failed автоматически не переписываются и не повторяются.

## Совместимость Параметров Модели

Параметры существующего провайдера проверяются отдельно от транспорта MAX.
Используйте только поддерживаемые моделью значения и учитывайте область
действия provider-level настроек. Реальную конфигурацию не публикуйте.

## Кружки

Bot API может не предоставлять доступное вложение пересланного кружка.
Не обещайте восстановление отсутствующего media сменой транспорта;
не подключайте пользовательскую сессию без отдельного разрешения.

## Приёмка И Откат

До выпуска: unit, настоящий BasePlatformAdapter, нативный цикл с активной задачей,
повторы событий, неоднозначный POST, чужая подписка, перезапуск во время возврата.
После выпуска: настоящий отказ только туннеля, успешный резервный polling,
автоматическое возвращение с тем же PID/работниками, один транспорт и неизменный
inbox. Телефонный голос и ответ модели проверяются отдельно.

Откат хранит конфигурационный delta, старый release и свежую SQLite-копию.
Нельзя накатывать старый inbox или снимать returning у живого poller вручную.
Перед возвратом версии проверяются реальные подписки, затем в свободное окно
останавливается gateway; marker и новые события остаются на месте.
