# Webhook MAX С Автоматическим Резервом

Версия плагина: 0.2.3. Функция включается явно для одного MAX-профиля.
Она не требует правки Hermes core или перезапуска gateway при самом отказе.

## Схема

```text
MAX -> HTTPS/443 на существующем VPS -> ограниченный SSH-туннель
    -> локальный ingress -> общий SQLite inbox -> штатный Hermes

При подтверждённом отказе VPS:
Hermes -> удаление своей Webhook-подписки -> GET-проверка отсутствия подписок
       -> прямой polling MAX -> тот же SQLite inbox и те же обработчики
```

На VPS нет bot-token, пользовательской сессии или постоянной копии переписки.
TLS заканчивается на VPS, поэтому он видит транзит сообщения; это не сквозное
шифрование до Hermes. Передача дальше защищена SSH. Локальный ingress слушает
только loopback; другие интерфейсы Hermes в интернет не публикуются.

## Настройка

В `platforms.max.extra` после проверки HTTPS-входа:

```yaml
webhook_url: https://your-domain.example/hermes/max
webhook_secret: YOUR_PRIVATE_SECRET
webhook_auto_fallback: true
inbox_path: /absolute/private/path/inbox.sqlite3
```

`inbox_path` должен совпадать у gateway и ingress и находиться на локальной ФС.
Не размещайте общий SQLite на VPS/сетевом диске. Секрет хранится приватно;
пример выше не является готовым config. Основной API-base остаётся прямым MAX,
иначе «резерв без VPS» не будет независимым. Списки доступа не расширяются.

У `MaxWebhookASGI` для внешнего ingress явно задаются `secret` и `path`.
Стандартный `scripts/max_webhook_server.py` делает это из переменных окружения.
`GET <path>/ready` требует тот же секрет и возвращает nonce для защиты от
ошибочно закешированной проверки. Этот endpoint не раскрывает очередь/переписку.
Лимит тела события — 1 MiB; время чтения ограничено. Медиа в запрос не встроены.

## Поведение При Отказе

- Проверка каждые 20 секунд: внешний HTTPS/ready и наличие ожидаемой подписки.
- Три последовательных неуспеха запускают попытку перехода. Реальное время
  зависит от сетевых тайм-аутов; не обещается переключение ровно за минуту.
- При наличии чужой подписки её не удаляют и polling не включают.
- После удаления своей подписки нужен успешный GET, подтверждающий отсутствие
  **всех** активных Webhook-подписок этого бота. Неясный ответ API блокирует переход.
- Очередь и выполняющиеся обработчики не заменяются/не отменяются. Сохранённые
  события Webhook и polling дедуплицируются по типу/ID сообщения или callback ID.
- Переход фиксируется в SQLite. После перезапуска резерв остаётся polling;
  автоматический возврат в Webhook отключён, чтобы исключить колебания режима.
- `/maxstatus` показывает реальный транспорт и состояние автоматического резерва.

Этот резерв возвращает прежде всего текстовую связь. Голосовые через polling
могут снова приходить неполными. При недоступности самого MAX API нельзя ни
подтвердить снятие подписки, ни гарантировать polling. Второй независимый
Webhook-вход — отдельный уровень доступности, не создаваемый одним VPS.
Ограничения хранения событий MAX и неоднозначные внешние действия не позволяют
обещать exactly-once или отсутствие любых потерь при длительном обрыве.

## Проверки До Переключения

1. Приватные копии конфигурации, старого plugin release и согласованных SQLite;
   отдельное восстановление и репетиция переноса актуальных состояний при откате.
2. Настоящий Hermes обязателен для контракта:

```bash
python scripts/max_loader_smoke.py --hermes-root /absolute/hermes
python scripts/max_policy_contract.py --hermes-root /absolute/hermes
python scripts/max_failover_contract.py --hermes-root /absolute/hermes
```

3. Новый ingress проверяется без изменения рабочей подписки: TLS, неправильный
   секрет, malformed JSON, durable ACK, duplicate, заполнение/восстановление очереди.
4. Останавливают только новый туннель, не VPS целиком; проверяют внешнюю ошибку
   и сохранение локальной готовности. В подготовительном испытании MAX API
   подменён, поэтому это ещё не живая приёмка снятия настоящей подписки.
5. Только после этих проверок, CI и свободного окна подключают pilot. Успешный
   POST регистрации дополнительно подтверждают GET-списком подписок.
6. На телефоне проверяют прямой голос, пересланный голос и пересланный кружок.
   Прямой кружок у владельца пока `blocked_ui`: кнопка отсутствует.

Контракт failover удерживает активный обработчик, переключает транспорт,
принимает команду из polling и подтверждает отсутствие повторного выполнения
того же события. Это тест с искусственным MAX API, не результат телефонной приёмки.

## Откат

Не восстанавливайте старую SQLite поверх новых сообщений. При возврате к прежнему
плагину сначала в свободное окно удалите только свою подписку и подтвердите её
отсутствие, остановите ingress, повторно проверьте отсутствие активных задач,
затем остановите gateway и сохраните текущий unified inbox.
Перенесите новые состояния и последний polling marker в совместимый legacy inbox;
прерванные `dispatching/accepted/processing` переводятся в `unknown`, не в `pending`.
Проверьте восстановленный файл старым классом хранилища и `quick_check`.

В конфигурации восстановите только прежний блок выбранного MAX-профиля, сохранив
последующие изменения TTS и остальных каналов. Затем верните старый plugin symlink
и запустите gateway. Проверяются оба канала. Для повторного включения Webhook
нужна отдельная согласованная операция; вручную удалять latch у работающего
резервного poller нельзя.
