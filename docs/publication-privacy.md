# Приватность Публикаций

Это правило проекта строже минимальных требований площадки: публикация
имени или IP сама по себе не обязательно нарушает политику GitHub, однако
непубличный контекст владельцев и их инфраструктуры в проект не включается.

## Перед Отправкой

1. Используйте официальные названия продуктов и нейтральные обозначения ролей.
   Личные обращения, прозвища, цитаты из приватных чатов и сведения о владельце
   не являются документацией продукта.
2. Проверяйте не только код, но и имена файлов, сообщения коммитов, author email,
   PR/issues/comments/reviews, релизы, wiki, логи, артефакты и изображения.
3. Не публикуйте действительные токены, ключи, cookie, пароли, подписанные URL,
   ID чатов, персональные контакты, домашние пути и адреса частной инфраструктуры.
   Для примеров используйте `example.com`, документальные IP и вымышленные ID.
4. Не стирайте лицензии или атрибуцию сторонних авторов. Для собственных
   коммитов используйте публичный GitHub login и GitHub noreply email.
5. Подробные эксплуатационные отчёты и результаты с реальными данными храните
   вне публикуемого репозитория. `.gitignore` не очищает уже опубликованную историю.
6. Проверяйте `git diff --cached`, локальную privacy-проверку и историю Gitleaks.
   Не добавляйте файлы вслепую через `git add .`; не обходите предупреждения
   scanner/push protection ради срочной публикации.

## Проверки

```bash
python scripts/publication_privacy.py --staged
gitleaks git . --redact=100 --log-opts="--all"
```

Проверка проекта не доказывает отсутствие всех персональных сведений.
Непубличные именования можно проверять локальным ignored-файлом
`.publication-private-patterns`: одна запрещённая строка на строку, без
добавления этого файла в Git. CI проверяет общие паттерны, локальная проверка
и ручное чтение покрывают приватный контекст. Никакой сканер не требует
передачи рабочих секретов внешнему сервису.

## Если Данные Уже Опубликованы

Сначала оцените доступ к секрету и согласуйте безопасный отзыв/ротацию. Затем
очистите текущие файлы и нужную историю, проверяя приватную резервную копию.
Не переписывайте опубликованные refs без согласования: меняются SHA и ссылки,
возможна потеря чужой работы. Используйте точные lease и отдельную копию.

Старые clones, forks, PR refs, кеши, логи и артефакты очищаются отдельно.
После переписывания не сливайте обратно старые ветки. Для серверных кешей
может потребоваться GitHub Support; удаление текущей строки не доказывает
полного удаления данных. В отчёте явно указывайте пределы проверки.
